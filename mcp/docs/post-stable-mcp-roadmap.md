# Post-Stable MCP Roadmap

## Base

- stable base commit: `f22b72fa6`

This roadmap describes what was implemented after the stable base, what should be preserved, and how to reintroduce future improvements without breaking Penpot behavior.

## Guiding Rule

The MCP is an orchestration layer over Penpot.

It should:

- call supported Penpot/plugin behaviors
- inspect document state safely
- instantiate and dock real library components
- attach metadata for traceability and code generation

It should not:

- recreate Penpot editor internals
- invent document layout state that the editor itself does not write
- couple new abstractions directly to fragile layout internals

## What Should Be Reintroduced First

### Phase 1. Operational Safety

Keep strengthening these areas:

- `plugin_connection_status`
- `inspect_canvas`
- strict postcondition checks
- no silent fallback to page root
- clear recovery guidance when plugin or stack is not ready

Success criteria:

- agents can tell whether the environment is ready before mutating the file
- agents cannot accidentally mutate the wrong container without noticing

### Phase 2. Library-First Composition

Improve the current safe behavior around connected libraries:

- library lookup heuristics
- better component matching
- safer `instantiate_library_component_into_slot`
- stricter validation of `parentId` after docking
- container-aware placement defaults for library instances:
  - slot padding via shared spacing scale
  - safe centering/containment defaults
  - margin only when asymmetry is intentional

Success criteria:

- agents can compose useful screens using existing Penpot libraries before resorting to manual drawing

### Phase 3. Safe Metadata For Traceability

Reintroduce only metadata-oriented structure:

- stable semantic ids in `pluginData`
- runtime-generated numeric sequence ids in `pluginData`
- widget/type/slot metadata
- optional naming conventions for layers, but only if harmless to the editor
- descriptive display names that can expose both numeric id and semantic id

Success criteria:

- users and agents can point to items reliably
- code generation can later map shapes back to semantic widget concepts

Decision notes:

- numeric ids should be generated by the MCP at runtime, not by modifying Penpot core behavior
- semantic ids should remain stable and descriptive
- layer naming can include numeric + semantic identity only if it remains editor-safe in manual validation
- the source of truth should stay in `pluginData`; layer names are a user convenience, not the primary machine contract

### Phase 4. Payload Ergonomics

Introduce a safer request-construction layer:

- compact request builders
- file-based or helper-generated payloads for tests
- no giant inline JSON blobs in shell commands

Success criteria:

- external agents can call the MCP without brittle raw payload handling

### Phase 5. Spacing And Container Discipline

Reintroduce the spacing-system idea conservatively:

- create or infer a reusable spacing scale before larger UI composition
- apply padding at the container level for boards, cards, panels, headers, and slots
- prefer gap + padding before child margins
- allow explicit centering only through safe container-level placement behavior

Success criteria:

- visible content is not glued to container edges
- library instances appear visually inside slots instead of floating against the parent bounds
- spacing defaults improve visual quality without mutating fragile Penpot layout internals

### Phase 6. Visual Regression Coverage

Bring back the visual smoke layer in a controlled way:

- MCP creates a simple board
- export it
- inspect it through Playwright
- verify manual editor actions still work

Success criteria:

- every higher-level helper can be judged both by visual output and by editor health

## What Must Not Be Reintroduced Blindly

- synthetic layout-child models that the current Penpot editor does not naturally produce
- large blueprint systems that write complex shape trees before the behavior is proven safe
- abstractions that only look correct in export but break selection, drag, or sidebar editing
- runtime tricks that try to emulate Penpot editor internals instead of using supported API operations

## Recommended Validation Gate For Every New MCP Feature

Every new helper should pass this exact sequence:

1. stack starts cleanly
2. plugin connects cleanly
3. file/page are detected correctly
4. helper creates or mutates content
5. created content can be selected
6. created content can be dragged
7. sidebar opens without `internal error`
8. export still works
9. `inspect_canvas` shows the expected tree and parentage

If a feature fails any step, it should not advance to the next phase.

## Immediate Next Implementations

1. Add a reusable operational troubleshooting section to MCP docs and scripts.
2. Improve library matching and slot placement without touching risky layout internals.
3. Add safe semantic metadata in `pluginData`, including numeric runtime sequence ids.
4. Reintroduce payload-builder support for tests and external agents.
5. Strengthen shared spacing and container padding defaults at the MCP layer only.
6. Rebuild the dashboard smoke in two variants:
   - conservative widget/manual board
   - library-first board using Pencil

## Summary

The safe path forward is:

- Penpot-first
- library-first
- inspect before mutate
- metadata before synthetic layout
- visual and editor-health validation after every step

That is the path that preserves the working stack while still allowing the MCP to become more useful for future agents.
